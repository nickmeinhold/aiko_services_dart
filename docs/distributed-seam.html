Crossing the distributed seam

Does the composed-mixin mapping survive leaving the actor? The scary part of the port — read from the Python source, proven with a two-isolate spike.

For Andy (geekscape) From Nick Status validated at the boundary the spike crosses Grounded in actor.py / discovery.py / transport_mqtt.py / parser.py / share.py
The finding, in three lines
  1. Nothing but a String ever crosses an actor boundary in Aiko. A remote call is a canonical S-expression (method_name arg1 arg2 …); the far side parses it and dispatches by name against its own local object. The composed mixin object never goes near the wire.
  2. So the isolate boundary is a non-issue for the mapping. The method table the composition mapping relies on stays inside one isolate by construction. Confirmed by a running two-isolate spike.
  3. One real porting nuance: Dart has no runtime getattr without dart:mirrors (banned in Flutter/AOT), so by-name dispatch becomes an explicit Map<String, Function> — built from the same method-name list the proxy already uses. Symmetric, bounded, codegen-friendly.

01The question handed forward

The composition mapping was validated within one actor — and explicitly left the boundary open.

That doc's §6 named the limitation precisely: “the composed object can’t cross an isolate boundary by reference.” Dart isolates don’t share memory; objects cross a SendPort by deep copy, and the intuition was that closures and a mixin’s method table are exactly what can’t ride along. If true, the elegant within-actor mapping might have a seam it can’t cross, and the port would need a different shape at the boundary.

The honest way to settle it is the same method that cracked the composition question: read where actor state actually crosses a boundary in the Python source, form an empirical hypothesis, then let a spike be the judge — here a real two-isolate one, not an in-process fake.

02The discovery: two Message classes

The word collides; the referent does not — and the distinction is the whole answer.

The transport Message publishes Strings over MQTT. The actor’s internal Message holds a live object reference and a closure — but it is manufactured locally, on the receiving side, to queue an incoming request onto that actor’s single-threaded event loop. It never leaves the process. When a String lands on topic_in:

# actor.py — the receiving side
def _topic_in_handler(self, _aiko, topic, payload_in):
    command, parameters = parse(payload_in)        # String -> (name, args)
    self._post_message(ActorTopic.IN, command, parameters)

# Message.invoke() — by-NAME dispatch, the Python getattr
target_function = self.target_object.__getattribute__(self.command)
target_function(*self.arguments)

The live-object Message is assembled here, from a command name and already-parsed String args — it was never on the wire.

03What a remote actor actually is: a list of method names

The remote-proxy builders in discovery.py and transport/transport_mqtt.py are identical in shape, and neither one ever touches the implementation object:

# discovery.py:_make_service_proxy — built from method-name STRINGS
def _proxy_send_message(method_name):
    def closure(*args, **kwargs):
        payload = generate(method_name, arguments)   # NAME + args -> String
        aiko.message.publish(target_topic_in, payload)
    return closure

# the proxy's method set comes from the INTERFACE, not the impl:
public_method_names = [n for n, m in getmembers(protocol_class, isfunction)
                       if not n.startswith("_")]
Why the inventory’s “Registrar has zero abstract methods” was the tell

The thing that represents a remote actor is a list of public method-name strings. That is why the interface inventory found Registrar’s contract is the wire protocol: the wire contract is exactly (method_name_string, string_serialized_args). There is no object to serialize because a remote actor was never an object — it is a topic path and a vocabulary of names.

All three layers of the seam run on this one mechanism — the same generate/parse canonical-S-expression codec (parser.py, whose functions are documented inverses):

04The spike: two isolates, only Strings between them

A composed mixin actor lives in isolate A. Isolate B holds only a SendPort and speaks S-expressions. The method table never crosses.

The composed CounterActor (three mixins — CounterMixin, GreeterMixin, ShareMixin — flattened onto one object, the same idiom as Category) is constructed inside the host isolate and never leaves it. Every property passes and dart analyze is clean.

// Built from the SAME method-name list a remote proxy uses.
String dispatch(CounterActor actor, String command, List<String?> args) {
  switch (command) {
    case 'increment': actor.increment(int.parse(args[0] ?? '0'));
                      return generate('count', [actor.count]);
    case 'greet':     return generate('greeting', [actor.greet(args[0] ?? '')]);
    // ...
    default:          // mirrors actor.py "Function not found"
                      return generate('error', ['Function not found: ' + command]);
  }
}

05A premise I had to correct by running it

The intuition “closures and mixin method tables can’t serialize” is false for spawned isolates — and knowing that sharpens the finding rather than threatening it.

Isolate behaviour isn’t reasoning-verifiable, so the spike sends a real composed mixin object to a spawned isolate and asserts what actually happens. Result: Dart deep-copies the object’s fields, and because spawned isolates share the program’s code (an isolate group), the method table resolves on the far side — the copied object’s mixin methods run fine.

So the seam dissolves from both directions

If Dart actors are isolates (same group): a composed mixin object can cross a SendPort — the fear was misplaced. But it doesn’t matter, because…

If actors are separate processes over MQTT (Aiko’s real topology): only bytes cross a network — no Dart object graph survives a hop, ever. And Aiko already designed for exactly this: everything is S-expr strings + by-name dispatch. The mixin never needs to cross, because Aiko never sends objects.

Either way the within-actor mapping is untouched. The boundary carries a method name and stringified args; the method table stays home.

06Verdict — scoped to what the spike crossed

◆ Validated at the isolate + wire-format boundary

For actor-to-actor messaging, state-sync, and discovery, the composed-mixin mapping survives the distributed seam because the seam never carries the mixin — it carries a canonical-S-expression command String, dispatched by name on the receiving side. A two-isolate Dart spike demonstrates the full round-trip (call, state delta, unknown-command diagnostic) with only Strings on the wire, and independently confirms Dart’s object-copy behaviour so the finding rests on a run, not a guess.

What this does not yet claim, held honestly:

  • The codec is spiked at the flat-command level, not the full canonical-S-expression grammar (nested lists, keyword dictionaries). parser.py remains the spec; a shipped codec needs interop tests against the Python generate/parse on real payloads.
  • The dispatch table was hand-written for one actor. At scale it wants generation from the interface’s method list — the same list the proxy is built from — not hand-maintenance.
  • Leases, leader election, and the Registrar state machine ride this wire but have their own liveness semantics not exercised here.

None of these reopen the seam; they are the build-out beyond it. The scary question — does the shape survive the crossing — is answered: yes, because the shape was never what crossed.
