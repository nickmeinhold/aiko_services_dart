The Constitution, read against the Dart port

Andy published the constitution on 2026-08-30. It is normative, it is 33 documents, and a good part of it turns out to be about code we have already written. This is the reading, with the evidence attached.

Upstream geekscape/aiko_services @ 702b896 Constitution landed c04baf8 — “E1: the constitution goes public” Read 2026-09-01
What changed for us
  1. A spec bug that would silently break any second implementation. The concept document says the length prefix is a byte count. parser.py counts code points. Measured both.
  2. The port holds evidence for open [VERIFY] items in Andy's own specification — §1.1's grammar extraction is an unfilled MUST, and RFC-0001 is that document.
  3. One design tension in the port is now settled by someone else. P1 is a Tier-1 identity principle and it forbids exactly the Dart idiom we kept reaching for.
  4. Our dispatcher is already compliant with a principle adopted after we wrote it — for a reason the code comment currently apologises for.
  5. One thing we recorded as a constraint to port is a violation Andy is scheduled to remove.

1What the constitution actually is

Not documentation. A governing tree with an enforcement mechanism.

constitution/ is 33 files, ~430 KB, under a naming scheme (G_II_ClearName.md) where the group letter carries the document's authority: p principles, s specifications, e plans, g guides, a analyses, t templates. Status is a closed vocabulary — normative binds, draft-for-verification does not yet, execution-plan is committed roadmap.

Two documents are the load-bearing ones for us: p_00_DesignPrinciples (normative; P1–P10, P12) and s_00_Specifications (draft-for-verification; RFC 2119 voice, decomposing into the AS-RFC series). When a specification is silent, decisions appeal to the principles — that is stated, not implied.

Worth noting given yesterday

Enforcement is .constitution-guard at the repository root — a staged-path denylist read by a pre-commit hook. Andy's gate is local too. Amending the guard file is itself a constitutional change.

2The finding: the length prefix is documented wrong

One word, in the one document a second implementer would build from.

documentation/concepts/utilities/parser.md — the file s_00 §1.1 names as the verification aid for the wire grammar — describes canonical symbols like this:

“The byte length prefixes the symbol, so has space becomes 9:has space (see Canonical S-expressions).”

The implementation counts something else. parser.py:109 is element = f"{len(element)}:{element}", and len() on a Python str is Unicode code points. For ASCII the two agree, which is why this has never bitten. For anything else they do not:

# CPython reference, geekscape/aiko_services @ 702b896
generate('cmd', ['héllo wörld'])  → (cmd 11:héllo wörld)
   code points 11   ·   UTF-8 bytes 13

generate('cmd', ['a 😀 b'])       → (cmd 5:a 😀 b)
   code points 5    ·   UTF-8 bytes 8   ·   UTF-16 units 6

So there are three defensible answers and the ecosystem currently contains all three: the doc says bytes, the reference implementation does code points, and the standard the doc cites defines canonical S-expressions in bytes. A Rust, C or TypeScript implementer reading parser.md and following its link would emit 13:héllo wörld. Python's parser would then consume 13 characters, run off the end of the symbol, and mis-frame the rest of the message — silently, and only for non-ASCII payloads.

The Dart port gets this right, deliberately

Our codec emits 5:a 😀 b, matching Python. That is not luck: Dart's String.length is UTF-16 code units and would have said 6. The codec counts runes. RFC-0001 §3 already pins it in normative voice — “<length> MUST equal the number of Unicode code points… not UTF-16 code units, not UTF-8 bytes, and not grapheme clusters” — and even rules on lone surrogates.

Our conformance fixture already pins this, which is why no new test accompanies this finding — (emoji 3:a 😀), (emoji 4:😀🎉 x) and a ZWJ family at (family 9:👨‍👩‍👧‍👦 x) are all present in both directions. Nine code points, one grapheme, seven glyph-forming characters: exactly the case where “byte”, “code point” and “character” give three different answers.

This is the highest-value thing in this document and the cheapest to act on: it is a one-word correction to parser.md, plus a sentence naming the divergence from the cited standard so the next reader does not re-derive it.

3§1.1 is an unfilled MUST, and we wrote the document that fills it

s_00_Specifications §1.1, verbatim:

“The canonical parser/generator in the reference implementation defines the tokenization, quoting and escaping rules. You MUST extract those rules here as a grammar (EBNF) rather than left implicit in utilities/parser.py. [VERIFY: exact quoting/escape rules, treatment of binary payloads, maximum practical message size over MQTT.]”

docs/rfc/0001-s-expression-wire-format.md in this repository is 373 lines of exactly that, pinned by 71 conformance vectors generated from the reference and cross-checked by two differential fuzz rigs. ADR-002 makes the same request from the other side: “the exact quoting and escape rules must still be extracted as normative grammar (s_00 §1.1 [VERIFY])”.

The template document t_01_OkfRfcTemplate defines the form such a document takes — the AS-RFC series, OKF front-matter plus an rfc: block, numbered requirements that conformance traces bind to, a mandatory Security Considerations section. Its worked example is numbered AS-RFC-2 for the Registrar protocol, which implies AS-RFC-1 is the wire grammar. Our file is already rfc/0001.

Deliberately not done

RFC-0001 has not been renamed or renumbered to AS-RFC-1. The template says RFC numbers are “immutable once assigned”, and the registry owns the numbers — which means Andy assigns them, not us. Claiming the number would be the kind of thing that is hard to walk back politely.

What the gap costs, concretely: our fuzz rigs found a \s divergence between Dart and Python worth 3604 mismatches in 40k atoms (recorded at tool/generate_codec_fixtures.py:77) that the entire golden-vector fixture ran straight past. The root cause was RFC-0001's own first draft deferring a normative character class to whatever the host language calls whitespace. An EBNF that does the same thing has the same hole, so §1.1's [VERIFY] is not clerical — it is the item most likely to break a second implementation, and it already broke ours once.

4P1 settles a design tension the port kept re-opening

Asynchrony is a property of the wire. It is not allowed to be a property of the language.

P1 is Tier 1 — identity, “trading any of these away produces a different framework”, and “the most expensive to reverse”. It reads:

“The framework therefore does not need, and deliberately does not use, Python async/await. Concurrency lives in the architecture rather than in the language.”
Forbidden: “introducing async def into framework interfaces… wrapping message sends in futures/promises as a core API.”

And s_02_InterfaceComposition states the rule that governs the whole composition design: “every interface method is asynchronous and returns nothing. A method is a message, and a message is fire-and-forget.”

Read carefully, the constraint is not “no concurrency” — it is that the asynchrony must live where a second implementation can see it, which is the wire. A Dart Future is invisible to a C firmware peer. This is the authoritative answer to something the port has circled repeatedly: three separate Dart mechanisms were tried to keep await ergonomics across the actor boundary, and each one moved the unsoundness somewhere less visible.

5Our reply type cannot express the sanctioned reply pattern

The dispatcher's contract is:

typedef CommandHandler = String? Function(List<Object?> arguments);

A handler computes a reply payload and returns it. s_02 §2 specifies replies differently:

“The response is itself a one-way message to an interface method the caller implements. Both halves are declared: a request/response pair is two Interfaces… making the protocol symmetric and traceable.” The request carries “the caller's reply topic (and a correlation token when the caller multiplexes)”.

This is a representation problem before it is a correctness problem. Our signature can express exactly one reply, computed immediately, sent to whatever topic the caller of dispatch() chooses. It cannot express: replying later, replying more than once, replying to a topic named in the request, or carrying a correlation token. Those are not exotic — they are the specified pattern.

It also connects to a defect we already recorded

We measured that do_request() in the Python reference has no correlation identity — two requests produce four handler firings, safe today only because all four call sites pass terminate=True. s_02 names the correlation token that would fix it, and the 2026-07-06 update to s_00 §5 says the do_request reply surface “is the reply-interface surface that this specification must define normatively”. Our measurement is evidence for an item Andy has already opened.

6The dispatcher is compliant with P12, by accident of Dart

P12 was adopted 2026-07-13, after our dispatcher was written. Its exposure rule:

“Every public API is deny-all by default, per method… Message dispatch never reaches a method that is not declared on a composed Interface.”

Python's dispatch is target.__getattribute__(command)(*parameters) — reflective lookup over the whole object, which is the shape P12 has to retrofit a guard onto. Dart has no runtime getattr without dart:mirrors, which is unavailable under AOT, so the port uses an explicit Map<String, CommandHandler>. That map is an allowlist, and there is no reachable path around it.

The code comment currently frames this as a workaround — “Dart's mirrors-free stand-in”. It is not a stand-in. It is the compliant shape, and Python is the one with the retrofit ahead of it.

The caveat, stated precisely

We are allowlist-shaped but the allowlist is not bound to an Interface declaration — handlers are registered by hand, so nothing stops registering a command that appears on no interface. P12's wording is “declared on a composed Interface”. Compliant in mechanism, unbound in provenance.

7Two things we recorded as constraints are actually defects being removed

ECProducer / ECConsumer as plain classes

Our notes record the boundary as “IS-A interface slices become Dart mixins; HAS-A plain classes (ECProducer/ECConsumer) become fields”. That reads the Python shape as a design to mirror. The constitution reads it as a violation:

“The June review verified two standing violations: ECProducer/ECConsumer are plain classes (making the framework's defining state primitive the only non-substitutable capability)… Both are to be normalized.” — P7 amendment, 2026-07-07

ADR-022 then rules that legacy non-compliance is “fixed retrospectively, not grandfathered”, with the remediation scheduled. So the Dart port should model these as Interface + Implementation and would be ahead of the reference rather than divergent from it. ADR-022 also hands us a decidable exemption taxonomy we can adopt directly — value/data types, presentation and CLI shells, pre-composition bootstrap — each exempt file carrying a header note naming its category.

The ECProducer incremental encoding

ADR-002 is blunt: values “must always round-trip through generate(), and never through f-string assembly. The known ECProducer incremental-update deviation is a bug against this decision, and not a competing convention.” The concrete symptom, from g_03: “values that contain spaces or nesting do not round-trip. Snapshot and incremental encodings can disagree for the same value.”

Our lib/src/service/share.dart imports dart:async and nothing else — it is the in-memory tree, with no wire encoding written yet. So we have not ported the bug, and we now have a ruling in hand before we build the publication path.

This inverts our standing verification stance, on exactly one surface

Every confidence claim in this repository is scoped as “parity with this reference, not correctness”. Here the constitution says parity is the bug. The rule is not “match Python”; it is “match Python except where a normative document says Python is wrong” — and until yesterday there was no document that could say so.

8Where the port has evidence Andy's testing strategy asks for

e_06_TestingStrategy is an execution plan establishing ADR-012 through ADR-016. Two of them point straight at us.

ADR-015 — “foundational primitives are tested directly and adversarially… because the trustworthiness of every golden trace depends on their correctness”. The named primitive is the S-expression parser/generator. Verified against current origin/master, not the July audit it is based on: src/aiko_services/tests/unit/ contains test_component, test_context, test_hook, test_pipeline_graph, test_registrar, test_share, test_stream_event, test_stream_lock — and no parser test. The module's only in-repo exercise is its own main() round-trip self-test.

ADR-016 — “the wire protocol is a cross-language contract. Conformance is mandatory… ‘The Python framework runs’ is never accepted as evidence that another implementation conforms.” M4 is defined as the golden traces pointed at a foreign binary over a real broker, with aiko_engine_mp first and “a future Rust/TS client next”. Dart is not on that list. It is, however, the implementation that currently exists.

One place where our evidence is stronger than the strategy that asks for it

M3 specifies the parser test as round-trip: parse(generate(x)) == x over a generated corpus. We learned the hard way that a self-round-trip proves self-consistency, not correctness — a codec can be self-consistently wrong, and ours was — the oracle-pinned vectors were green while a differential run against CPython produced 3604 mismatches in 40k atoms. Differential-against-a-second-implementation strictly dominates round-trip, and the Dart port is what makes it available. This is worth offering as an amendment to M3, not as a criticism — e_06 was written when only one implementation existed.

10Bookkeeping the reading turned up

  • Task #2269 is answered. Not OpenSpec — the convention is the AS-RFC series with OKF front-matter, numbered requirements bound to conformance traces, and updates/obsoletes discipline. t_02_OkfTaxonomy holds the closed vocabularies our documents should adopt.
  • RFC-0001's own header is stale. It claims “15 encode + 15 decode vectors”. The fixture actually holds 35 generate, 30 parse, 6 parse-error and 5 divergence entries. Counted, not remembered.
  • P9 has a rule our mailbox design must meet. “No new queue, cache or buffer enters the runtime without a bound and a stated overflow policy.” We measured that a Dart SendPort applies no backpressure whatsoever — 400k messages accepted in 478 ms for +345 MB RSS — so the bound has to be built above it, and named.
  • P2's amendment is generous to Dart. It concedes that Python mailboxes give messaging isolation but not scheduling isolation, so “the unit of scheduling isolation is the OS process”. Dart isolates give real scheduling isolation in-process, which is a capability the reference cannot offer. Worth raising as a genuine question rather than assuming it is welcome.
