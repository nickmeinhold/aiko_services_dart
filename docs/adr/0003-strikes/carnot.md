## CarnotCodeCarver's Design Strike

**Verdict:** DISSOLVE

**Summary:** CarnotCodeCarver review: no real engine matches the Carnot cycle; a reviewer's job is to say how far short we are. This ADR correctly rejects `Future`, correctly deletes synchronous `ReplyNow`, and correctly recognizes state observation as preferred. But it then builds a central `Reply` return type that pulls the design back toward return-value thinking. The simpler structure is: handlers return nothing; request methods that need answers carry a reply destination object in their input; later sends are just normal outbound messages; most query-like cases move to observed state. Dijkstra: "Simplicity is prerequisite for reliability." This type is wasted work because the protocol already has the mechanism: messages to topics.

**Fatal flaws:**
- The nullable `CorrelationToken?` smuggles protocol cases into field nullability. s_02 says a token exists "when the caller multiplexes"; that is not a nullable attribute of one uniform reply shape, it is two request/reply protocols: non-multiplexed reply destination and multiplexed reply destination. Model the destination as separate shapes, e.g. `ReplyAddress(topic)` versus `CorrelatedReplyAddress(topic, token)`, or keep it entirely in the owning interface's request type. Nullable token means every consumer must remember a conditional invariant the type system could have represented.
- `Deferred` is the worst heat leak: it records an obligation while enforcing none of it. The ADR admits this and calls it acceptable, but that is exactly the design smell. Returning `Deferred(topic, token)` creates a third state: "trust me, I will send later." s_02 and P1 do not require such an acknowledgement object. If the handler will send later, it should retain the reply address and return nothing. If the caller needs completion, the sanctioned idiom from P1 is command then observe, not a phantom debt marker.
- The ADR's Correction 3 is half right and half misfiled. s_02's third pattern covers continuous result sequences on `topic_out` or Pipeline edges. That excludes telemetry/frame streams from `Reply`, yes. But "reply-N-times" as a phrase is ambiguous: if it means a finite multi-message response to one genuine request, s_02 does not clearly assign that to `topic_out`; it may be an owning-interface reply protocol with repeated messages and correlation. The ADR overclaims by saying reply-N-times is categorically pattern 3 rather than asking whether the owning reply interface permits multiple response messages.
- `ReplyError` as a separate case is machinery in the wrong layer. s_02 says a failed request produces an error message to the reply topic, or an error value in shared state, per the owning interface's spec. That points to protocol payload shape, not a framework-wide `ReplyError` variant. A failure is a message on the caller's reply interface. If that interface has `found`, `not_found`, `failed`, or `error` methods, those are payload/protocol cases under `ReplyTo`, not a universal dispatcher case. The type centralizes what s_02 says belongs to the owning interface spec.
- The `Reply` return type does not violate P1 as literally as `Future` would, because it is not awaitable and does not promise a value at the call site. But it violates the pressure of P1 by making framework handler return values a core API. P1 says remote service methods never return values; s_02 says replacements for returns are state observation, reply-to messages, and streams. A handler returning `Reply` is an internal dispatch convention, not a wire return, but it trains the framework surface around return-shaped control. That is too close to the forbidden reflex.

**What holds:**
- The ADR is right that `String?` is an impoverished representation: payload versus no payload should not be encoded as nullable string.
- It reads s_02 correctly that there is no synchronous `ReplyNow`: responses are separate one-way messages to a caller-declared interface/topic.
- It reads P1 correctly that `Future`/promise request-response must not become a core API. Feynman: "The first principle is that you must not fool yourself." Calling a `Future` by another name would fool the design; this ADR avoids that literal error.
- It correctly notices the unknown-command divergence: `actor.py` logs diagnostics and publishes nothing, while s_02 allows an error message only when the request has a reply topic, otherwise shared state/local logging is the only available path.
- It correctly surfaces the danger that making replies convenient makes the less-preferred pattern attractive.

**If RECAST, what to fold back:**
- Fold back to no central `Reply` type. Change `CommandHandler` toward `void Function(List<Object?> arguments, HandlerContext context)` or equivalent, where `context` exposes ordinary `publish` and possibly parsed request metadata. The handler sends if the owning protocol says to send.
- Represent reply destination in the request protocol, not in a dispatcher return. Use separate destination shapes for correlated and uncorrelated cases instead of `CorrelationToken?`.
- Put errors in the owning reply interface as payload/message variants. Do not create framework-global `ReplyError` unless there is a separately specified universal error protocol.
- Delete `Deferred`. Later reply is just retaining the reply address and sending later. The obligation is enforced, if at all, by endpoint timeout/state observation, not by a return variant.
- Carnot question answer: yes, the simpler structure deletes this type entirely. s_02 says state observation is the preferred replacement for most returns, and genuine replies are already modeled as one-way messages to caller interfaces. Hamming: "The purpose of computing is insight, not numbers." The insight here is that `Reply` preserves the return slot; deleting the slot is the design.
