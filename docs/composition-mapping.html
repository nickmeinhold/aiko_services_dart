Aiko Services · Dart port · design note

The composition mapping — Python compose_instance → Dart mixins

The one load-bearing decision the whole port hangs on: does Aiko's bespoke Pythonic composition system map to idiomatic, performant Dart — or does the port become decoration on top of an un-Dart-like machine? Answered by reading the source and proving it with a running spike.

◆ Verdict — validated for the current object model

For the object model as it stands today, Dart mixins look like the right target — and not by luck. Aiko's Interface + compose_class + call_init reads as a hand-rolled emulation of a compile-time trait system, much of which Dart provides natively; for the composition call sites in the current framework, the dynamic reflection appears to be a Python workaround rather than a load-bearing requirement. Every property the spike exercises is preserved, checked against Category's real two-branch shape. This is a validated within-actor mapping, not a proof about the whole port — the distributed seam (isolate boundaries, MQTT transport, discovery) is explicitly out of scope here (see §6).

Spike: spike/composition/ — 5 property tests, dart analyze clean, all green on first run.

1 · What the Python system actually is

Reading component.py and context.py line by line, the composition system has three moving parts. It looks exotic; it is a trait system.

① Interface = abstract methods + one registered default impl

An Interface is a pure-abstract class (every method @abstractmethod) that registers one default implementation string into a shared class-level registry:

class Actor(Service):
    Interface.default("Actor", "aiko_services.main.actor.ActorImpl")
    @abstractmethod
    def run(self): pass

② compose_class = copy the impl methods onto a synthetic class

compose_class builds an empty FrankensteinClass(seed) and, via getmembers+setattr, copies each implementation's concrete methods onto it — with the precedence rule “concrete beats abstract; don't replace an already-concrete method.” That is mixin linearization, done at runtime because Python has no compile-time mixins.

③ call_init = idempotent, name-keyed init chain

Because the synthetic class has no real constructor chain, each slice initializes itself through context.call_init, guarded so a shared ancestor reached through a diamond initializes once:

def call_init(self, caller, implementation_name, context, **kwargs):
    if not self.is_initialized(implementation_name):
        callee = self.get_implementation(implementation_name)
        callee.__init__(caller, context, **kwargs)   # run impl's __init__ on the ONE self
        self.set_initialized(implementation_name)

2 · The empirical finding that defuses the landmine

The scary part was impl_overrides — the ability to swap an interface's implementation at compose time, which smells like it needs runtime reflection Dart can't do cheaply. So the decisive question: is implementation-swapping ever data-driven at runtime, or always a static wiring choice?

▸ Checked every call site

All 15+ compose_instance(...) call sites in the framework pass no impl_overrides. The override parameter — the only genuinely dynamic capability — is dead in the main codebase. Each interface declares exactly one default; binding is 100% static. Test implementations are wired as separate composed classes, never runtime swaps.

That was the load-bearing risk for the mapping question. For the current framework's call sites, static binding maps to a compile-time class choice in Dart — no reflection needed. (This checks the obvious dynamic path; it does not rule out dynamism arriving via user/extension code, metaclasses, or setattr outside the core composition functions — those stay open.)

4 · The Dart mapping

One Python Interface+Impl pair becomes one Dart mixin: abstract methods stay abstract members, the impl body becomes the concrete method, on constraints encode the “needs” edges, and a per-slice _initX method stands in for the constructor mixins can't declare. The real graph —

Service(ServiceProtocolInterface, Hooks)   // Service is itself a composition
Actor(Service)                             // Actor needs Service
Dependency(Interface)                      // standalone; service may be null
Category(Actor, Dependency)                // the acid test — two branches

— maps to:

mixin CallInit {                    // port of context.call_init
  void callInit(Context ctx, String slice, void Function() init) {
    if (!ctx.isInitialized(slice)) { init(); ctx.setInitialized(slice); }
  }
}

mixin ServiceMixin on CallInit, HooksMixin {
  late String serviceName;
  void initService(Context ctx) => callInit(ctx, 'Service', () {
        initHooks(ctx);              // cascade — mirrors ServiceImpl reaching Hooks
        serviceName = ctx.name;
      });
  String describe() => 'Service($serviceName)';   // default, overridable
}

mixin ActorMixin on CallInit, HooksMixin, ServiceMixin {
  late Map<String, Object> share;
  void initActor(Context ctx) => callInit(ctx, 'Actor', () {
        initService(ctx);           // ActorImpl.__init__'s first line
        share = {'lifecycle': 'ready', 'running': false};
      });
  @override String describe() => 'Actor($serviceName)';  // P3: later mixin wins
}

mixin DependencyMixin on CallInit {
  Object? service;                  // P5: null = absent, a NORMAL value
  void initDependency(Context ctx, {Object? serviceFilter}) =>
      callInit(ctx, 'Dependency', () { /* set fields */ });
}

class Category with CallInit, HooksMixin, ServiceMixin,
                    ActorMixin, DependencyMixin {
  Category(Context ctx, {Object? serviceFilter}) {
    initActor(ctx);                              // Actor → Service → Hooks
    initDependency(ctx, serviceFilter: serviceFilter);
  }
}

This is a near-mechanical transcription of CategoryImpl.__init__, which calls call_init("Actor") then call_init("Dependency", ...). The Dart version is compile-checked — a missing slice or bad on edge is an analyzer error, where Python only fails at compose time.

Why the per-slice _initX method, instead of constructors?

Dart mixins can't declare generative constructors. That sounds like a limitation until you notice it's exactly why Python needed call_init: the FrankensteinClass has no constructor chain either, so each slice initializes itself explicitly. The Dart _initX(ctx) + guard is the same pattern, made compile-safe. The one shared ancestor (Service, reached via a diamond) still inits once — proven below.

The diamond test is the honest one: Category's two branches are actually disjoint (Dependency is not a Service), so DiamondNode constructs a genuine diamond — Actor and Registrar both on ServiceMixin — to exercise the guard rather than just trust it.

6 · What this does not yet prove

Honest edges, so the next builder engages them rather than inherits them:

  • Isolate boundaries. The spike is single-isolate. Aiko's runtime is isolate-per-actor; mixin state is fine within an isolate, but the composed object can't cross an isolate boundary by reference. That's the isolate-per-actor design note's territory, not this one's — the composition mapping holds inside an actor.
  • Generics / self-types. None of the sampled interfaces needed F-bounded generics. If a later interface does, the mixin on mechanism may need a type parameter — unverified.
  • The full inventory. This validates the mechanism on Category's shape. The per-interface method inventory is now written up in the interface inventory — every Interface, its contract, and its target Dart shape, with the deepest diamond (HyperSpace) proven in the same spike.
