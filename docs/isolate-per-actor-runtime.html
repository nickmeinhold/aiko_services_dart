An isolate-per-actor runtime for Aiko in Dart

How Aiko's distributed actor model maps onto Dart's isolate groups, and the build sequence I'd propose.

For Andy (geekscape) From Nick Status proposal, for discussion Grounded in aiko_services category.py / hyperspace.py / share.py
The ask, in three lines
  1. Build the single-isolate EC client first. ECProducer / ECConsumer + the s-expression codec + Registrar discovery, over one MQTT connection. This is the MVP that unblocks the chat gateway and proves interop against the Python reference.
  2. Then the MessageBus + isolate-per-actor runtime. The v2 shape that lets Dart host native Categories / HyperSpace, not just consume them.
  3. Two things I need you to confirm (bottom of this note) so I'm not building on a wrong read of your scheduling model or your composition layer.

01Two "actor models", at different layers

The word collides; the referent does not. Getting this distinction right is what keeps the port faithful.

Dart isolates are the local actor model: concurrency isolation inside one VM, messages over in-process ports. Aiko's Actor is the distributed actor model: a thing addressable by other processes and other languages over a broker. They are complementary, not substitutable.

Dart isolateAiko Actor
isolation boundaryan OS-level heap; no shared mutable memorya network identity: an MQTT topic path
transportSendPort / ReceivePort in-VMMQTT cross-process / cross-host
scopeintra-process concurrencyinter-process distribution
isolation enforced bythe language (cannot share state)convention (everything should go via share / EC)

The consequence: cross-language interop (Dart ↔ Python) is always MQTT, regardless of isolate choices. Isolates only govern how Dart actors relate to each other in-process.

02What Dart isolate groups changed

The relevant recent development. Since Dart 2.15 (and on by default shortly after), a spawned isolate joins the spawner's group, and the group shares one GC-managed heap plus program structure, JIT code, constants and interned Strings. Measured effect: roughly 10× faster spawn, 10× lower base memory, 8× faster inter-isolate communication.

The nuance that makes it usable

Sharing the heap did not relax the semantics. Isolates in a group still cannot touch each other's mutable state and still communicate only by message-passing. It is a VM implementation optimisation, not a change to the programming model. So the cost objection to "one isolate per actor" mostly dissolves: it is one shared heap and one GC across many cheap isolates, while the hard no-shared-mutable-state guarantee stays intact.

Worth separating from a newer, unshipped proposal for genuine shared-memory multithreading (language working-group doc 333). I would not design against that yet; isolate groups are the stable ground.

03The invariant the design must preserve

The topic is the only address.

A Python actor publishing to #general has no idea whether the recipient is a sibling in the same process or a service on another host. That location transparency is the actor model here, and it is exactly what your uniform-MQTT approach buys. So "one isolate per actor" cannot mean actors wiring SendPorts directly to each other: direct port-wiring makes an actor know its peers' isolate identities, which is location-aware, the opposite of what we want. The fix is to keep the topic bus as the single namespace and put a router between actors and both transports. Which is precisely what aiko.process already is on the Python side: the process-level singleton owning the one MQTT connection for all in-process actors.

04Proposed topology: a MessageBus isolate

The faithful translation of "aiko.process owns one MQTT connection for N in-process actors" is one MessageBus isolate that owns the single MQTT socket, with each actor in its own isolate holding a port-pair to the bus.

The bus does one job: route a (topic, payload) to every subscriber. When an actor publishes, the bus delivers to any local isolate subscribed to that topic via its port (the fast path, no broker round-trip) and publishes to MQTT, so remote actors and mosquitto_sub both still see it. That dual delivery is the key: it keeps your observability property intact while giving in-VM peers a shortcut. Local subscribers get a port copy; the broker still sees everything for anyone remote.

05Where share / ECProducer / ECConsumer land

This is where isolate-per-actor pays off cleanly:

Aiko pieceDart homeWhy it fits
sharethe actor isolate's private Mapisolate memory-ownership enforces the discipline you ask for by convention. The single best-fit mapping in the port.
ECProducerinside the actor isolateupdate()/remove() mutate share locally, then hand a delta to the bus port. Never touches the network directly, same as calling aiko.message.publish.
ECConsumerany subscriber isolate (or remote)just sends (share …) through the bus. Its reply topic is backed by an inbox port when local, a real MQTT topic when remote, and it does not know which.

The EC wire protocol, as I read it from share.py

Confirming my read so the Dart codec is faithful, please correct anything wrong:

  • (update <key> <value>)producer → topic_state, delta
  • (remove <key>)producer → topic_state, delta
  • (share <reply> <lease> <filter>)consumer → producer topic_control, a leased subscribe
  • (sync <topic>)producer → topic_state, snapshot complete

The producer listens on topic_control, publishes deltas on topic_state; a subscribe triggers a full snapshot to the consumer's private reply topic, then a stream of deltas. Subscriptions are leased and expire unless renewed, which is the distributed GC. All of that ports directly; the lease timer is the only piece that needs care (see below).

06The runtime, in Dart

Illustrative shape, not compiled. It exists to make the mapping concrete, not to be shipped as-is.

// The message that crosses every port and the MQTT wire alike
class BusMessage {
  final String topic;    // the ONLY address
  final String payload;  // "(update entries.x (...))"
  const BusMessage(this.topic, this.payload);
}

// Entry point of each actor isolate
Future<void> actorMain(ActorBootstrap boot) async {
  final toBus = boot.busSendPort;             // publish here
  final inbox = ReceivePort();                // bus delivers here
  toBus.send(RegisterPort(inbox.sendPort));

  final share = <String, dynamic>{};          // isolate-private state
  final ec = ECProducer(
    share: share,
    topicState:   '${boot.topicPath}/state',
    topicControl: '${boot.topicPath}/control',
    publish: (t, p) => toBus.send(BusMessage(t, p)),
  );
  toBus.send(Subscribe('${boot.topicPath}/control', inbox.sendPort));

  await for (final msg in inbox) {            // the actor's event loop
    if (msg is BusMessage) ec.handleControl(msg);
    // ... actor-specific handlers ...
  }
}

class ECProducer {
  final Map<String, dynamic> share;
  final String topicState, topicControl;
  final void Function(String, String) publish;
  final _leases = <String, Lease>{};          // remote subscribers only

  void update(String key, dynamic value) {
    _setPath(share, key, value);
    publish(topicState, '(update $key ${_wire(value)})');
  }
  void remove(String key) {
    _removePath(share, key);
    publish(topicState, '(remove $key)');
  }
  void handleControl(BusMessage m) {
    final c = parseSExpr(m.payload);
    switch (c.verb) {
      case 'share':  _synchronize(c.reply, c.lease, c.filter); break;
      case 'update': update(c.key, c.value); break;
      case 'remove': remove(c.key); break;
    }
  }
  void _synchronize(String reply, int lease, String filter) {
    publish(reply, '(item_count ${share.length})');
    share.forEach((k, v) => publish(reply, '(update $k ${_wire(v)})'));
    publish(topicState, '(sync $reply)');
    _leases[reply] = Lease(lease, onExpire: () => _leases.remove(reply));
  }
}
MessageBus isolate · the only thing that touches MQTT 
class MessageBus {
  final _localSubs = <String, List<SendPort>>{};  // topic -> local inboxes
  late final MqttClient _mqtt;                     // the single connection

  void onActorPublish(BusMessage m) {
    for (final p in _matching(_localSubs, m.topic)) p.send(m);  // in-VM fast path
    _mqtt.publish(m.topic, m.payload);             // remote + observability
  }
  void onMqttMessage(String topic, String payload) {
    for (final p in _matching(_localSubs, topic))
      p.send(BusMessage(topic, payload));
  }
  void onSubscribe(Subscribe s) {
    _localSubs.putIfAbsent(s.topic, () => []).add(s.port);
    _mqtt.subscribe(s.topic);                      // so remote publishers reach local subs
  }
}

07Two subtleties

Leases matter, but only for remote subscribers

For a local consumer isolate, liveness is free: if the isolate dies, its ReceivePort closes and the bus drops it immediately, no timeout needed. For remote MQTT subscribers you must keep the lease/renew mechanism, because a dead remote process gives no such signal and lease expiry is the only death detector. So the Dart bus runs leases for MQTT subscribers and port-liveness for local ones. Faithful to intent, cheaper locally.

The composition layer gets easier, not harder

Under isolate-per-actor, cross-actor composition disappears entirely, because actors compose only via messages, so there is no shared object graph to assemble. What remains is intra-actor composition (Category is-a Actor is-a Dependency), all inside one isolate, which Dart mixins handle: class Category with ActorMixin, DependencyMixin. The isolate boundary does the work your compose_instance machinery does in Python. This is the piece I most want your read on (below).

The deeper payoff

Three Aiko invariants move from "please" to "guaranteed": location transparency (topic bus), state isolation (isolate memory ownership), and local lifecycle (port closure signals death). The Dart port can enforce by language what the Python reference enforces by convention.

08Roadmap: what to build, in order

StageScopeUnlocks
MVP · now Single isolate, one MQTT connection. s-expression codec + ECConsumer/ECProducer + Registrar discovery. The chat gateway. Proven EC interop against the Python reference. This is your July-9 scope exactly.

Building the bus first would be machinery ahead of the simple pick. The single-isolate client is the thing that actually unblocks the gateway; the bus earns its place only once we want to run Categories natively in Dart.

09Two things I need you to confirm

Question 1 · scheduling

How does one Python Aiko process schedule its many in-process actors: a single event loop driven by MQTT callbacks, or threads? I am inferring single-loop from aiko.process.run(). If it is threads, the "one isolate, many logical actors" default for the Dart MVP shifts from a faithful translation to a deliberate divergence, and I would want to name that.

Question 2 · composition

Your Interface.default / context.call_init / compose_instance layer is dynamic in a way Dart has no direct analogue for. My plan is to render intra-actor composition as Dart mixins and let the isolate boundary absorb the cross-actor part. Does that lose anything you rely on, for example runtime re-composition or interface swapping that the Dart-static version would forbid?
